# KRUG Mini App 0.1 — Booking UX Foundation

Отдельное клиентское приложение для записи в студию КРУГ. HTML / CSS / vanilla JS, без зависимостей, сборки и backend. Внутренняя CRM не импортируется, не изменяется и не получает данные Mini App.

## Зачем этот патч

Проверить самостоятельную запись клиента до подключения реальной инфраструктуры: услуга → длительность → дата → время → контакты и подтверждение. Выбор времени и цены становится понятным на телефоне; проверка UX сейчас позволяет подготовить API под проверенный сценарий.

## Структура

- `index.html` — самостоятельная точка входа.
- `styles.css` — мобильный интерфейс, фирменные цвета, safe-area и нижняя CTA.
- `app.js` — экраны, навигация, `bookingDraft`, обработка формы.
- `booking.js` — чистые правила цены, длительности, московских дат и свободных интервалов.
- `data.js` — mock-каталог, расписание и асинхронный API-адаптер.
- `telegram.js` — необязательная интеграция с существующим `window.Telegram.WebApp`.
- `logo.svg` — самостоятельная копия фирменного логотипа.
- `tests/booking.test.cjs` — проверки правил и хранения штатным Node test runner.
- `tests/browser.cjs` — мобильный сценарий через внешний Playwright, без установки зависимостей в проект.

Публиковать отдельно только содержимое `mini-app`; не направлять клиентов на корень внутренней CRM. В этом патче публикация и изменение существующего preview не выполнялись. Для локального просмотра можно открыть `index.html` или раздавать эту папку статическим HTTP-сервером. При смене origin данные браузера не переносятся.

## Flow и данные

Главная содержит «Записаться», «Мои записи» и четыре быстрых входа. «Другие услуги» открывает полный каталог, включая утреннюю запись. Почасовая запись проходит пять шагов; fixed-услуга пропускает длительность и использует `defaultDurationHours` и `price`.

Выбранные данные находятся в `bookingDraft`, а не только в DOM. Возврат назад сохраняет выбор и введённые контакты. Изменение услуги или длительности сбрасывает стартовое время. Создание повторно проверяет тариф и доступность; цена из UI не считается источником истины. `requestId` защищает повторный запрос от дублей. При поддержке Web Locks сохранение сериализовано между вкладками.

Заявки имеют статус `request` («Заявка») и сохраняются в отдельном ключе `krug_mini_app_bookings_v1`. «Мои записи» фильтрует `clientId: krug-mock-client`. Все посетители конкретного браузерного origin используют одну mock-личность; авторизации и реальной изоляции пользователей здесь нет. Все сохранённые неотменённые записи занимают одну общую студию. Данные и ключи CRM не используются.

Ошибки чтения/записи localStorage показываются пользователю; повреждённые данные не заменяются пустым массивом. Отмена и перенос представлены отключёнными кнопками. Платежей, сотрудников, финансов и CRM-экранов нет.

## Pricing

Все указанные в задании тарифы перенесены точно, итоговая цена выбирается по длительности; округлённая средняя цена за час вторична. Для «Запись утром» и «Аренда» в задании не задан тариф за 2 часа: кнопка видна, но отключена. Цена не интерполируется.

Каталог различает `pricingType: hourly | fixed`. Fixed-услуги не придуманы для публичного каталога: архитектура проверяется отдельной тестовой фикстурой. Для fixed-записи обязательно задавать её длительность занятия студии через `defaultDurationHours`.

## Availability

Публичный интерфейс адаптера:

```js
getServices()
getService(id)
getAvailability(date)
getAvailableSlots(date, durationHours, serviceId /* optional */)
createBooking(data)
getMyBookings()
```

Все методы возвращают Promise. UI обращается к адаптеру и не читает localStorage. Для будущего HTTP API заменяется адаптер, сохраняя этот контракт.

Mock-правила: ближайшие 21 день, 09:00–23:00 МСК, старт каждый час, воскресенье закрыто. В остальные дни есть занятый интервал 13:00–15:00 или 17:00–19:00. Прошедшие слоты скрываются по московскому времени независимо от часового пояса браузера. Для утреннего тарифа принято предварительное правило старта до 12:00; реальное расписание и это ограничение нужно согласовать перед 0.2.

Проверяется весь интервал `[start, end)`, а не только начало. Например, при занятости 13:00–15:00 пятичасовую сессию нельзя начать в 10:00; старт в 15:00 допустим, если до 20:00 всё свободно. Соприкасающиеся границы не конфликтуют. Нет помещений и параллельной записи.

## Telegram preparation

`initTelegram()`, `getTelegramUser()`, `expandApp()`, `closeApp()` безопасны без Telegram. При наличии WebApp вызываются `ready`, `expand`, оформление, системная кнопка «Назад», учитываются safe-area события. Имя и username могут предзаполняться, но `initDataUnsafe` не используется для аутентификации или определения mock-client.

Удалённый SDK не загружается в 0.1. Для запуска в настоящем Telegram требуется подключить официальный WebApp SDK перед адаптером и настроить вход Mini App. Реальный клиент Telegram не тестировался; проверена заглушка WebApp. Сообщения и заявки в студию не отправляются — на экранах явно указан демо-режим.

## Проверки 0.1

Выполнено:

- `node --test mini-app/tests/booking.test.cjs`: 4 теста — все тарифы, fixed-цена, пятичасовой интервал, границы, прошедшее время, сохранение, повторный запрос, пересечение услуг, фильтрация клиента, повреждённое хранилище и ошибка записи.
- Проверка синтаксиса JavaScript.
- Браузерный сценарий в headless Edge / Playwright на **390×844, 360×800, 430×932**: восемь экранов, цена 3 300 ₽ за 3 часа, возврат, сохранение контактов, подтверждение, success, «Мои записи», reload, запрет пересечения с другой услугой. Горизонтального переполнения и ошибок console/pageerror не обнаружено.
- Fixed-фикстура пропускает длительность. Telegram-заглушка проверяет ready/expand/back/show/hide/close.
- Вручную просмотрены скриншоты главной, календаря, подтверждения, успеха и списка записей.

Браузерный тест запускается с внешним runtime:

```text
node mini-app/tests/browser.cjs <absolute-path-to-playwright> <existing-screenshot-directory>
```

Playwright и браузер служат только проверке, не являются зависимостями приложения. Тест создаёт временный статический сервер и изолированные браузерные контексты. CLI agent-browser в окружении отсутствовал. Физические iPhone/Android, экранная клавиатура и реальный Telegram не проверялись. Сценарии внутренних платежей/сотрудников CRM к отдельному Mini App не относятся.

Затем подключить передачу заявок в студию, подтверждение в Telegram, перенос/отмену, настроить отдельный HTTPS preview и провести тест на реальных устройствах. Backend, синхронизация, SDK и отправка сообщений в 0.1 не реализованы.

Из существующего проекта ничего не удалено; все изменения ограничены новой папкой `mini-app`.
